# 2026-10-24 맥 저장 공간 읽기 전용 진단

확인한 큰 항목은 **`~/Project` 515.34GB**, 그 안의 **`CDS-wt` 424.14GB**와 CDS 본체 57.81GB다. Chrome 앱 복제본 638개 누적도 확인했다. 다만 시스템 설정의 **시스템 데이터 772.07GB를 항목별로 정확히 분해한 결과는 아니며**, 이 폴더들을 삭제하면 얼마가 확보되는지도 확정하지 않았다. GB는 10억 바이트 기준이다.

## 상하위 경로를 중복해서 더하지 않은 주요 항목

아래 표는 포함 관계가 겹치는 하위 폴더를 별도 합산하지 않는다. APFS(맥 파일 저장 방식)의 공유 블록까지 제거한 독점 물리 용량 표는 아니다. 측정 시점도 서로 달라 총합을 시스템 데이터 값과 대조하지 않는다.

| 경로 | 관측 크기 | 근거와 포함 관계 |
|---|---:|---|
| `~/Project` | 515.335GB | 직접 항목 19개 모두 측정. 아래 CDS 수치는 이 안에 포함 |
| `/private/tmp` | 약 110.64GB | 이전 세션 측정 재사용. CDS 임시 작업 사본 약 76.48GB 포함 |
| `~/Library` | 약 67.43GB | 이전 세션 측정 재사용, 권한 제한 있음 |
| `~/.claude` | 약 45.15GB | 이전 세션 측정 재사용 |
| `/Applications` | 25.478GB | 이번 읽기 전용 측정 |
| `~/.codex` | 약 12.20GB | 이전 세션 측정 재사용 |

`CDS-wt`는 직접 하위 폴더 89개와 파일 1개, **90/90항목**을 측정해 **424,142,188,544바이트**를 집계했다. CDS 본체는 **57,809,522,688바이트**, 그 안의 `report`는 **40,139,710,464바이트**다. 대표 작업 폴더 `codex-oracle-bounded-read-20261024`는 총 7.628GB 중 `report` 5.367GB·`assets` 1.550GB·`review` 0.633GB로 세 폴더가 약 99%다. 표본 두 곳의 `.git` 파일은 실제 CDS worktree(프로젝트를 따로 작업하는 사본) 등록 위치를 가리켰다. 이것으로 고유 자료가 없거나 삭제해도 안전하다고 판정하지 않는다.

이전 세션 값은 이번 새 전체 측정으로 포장하지 않는다. 일부는 Wavvy 정리 전 시점의 값일 수 있다. 최신 전체 측정 시점의 Data 볼륨 사용량은 약 907.20GB, 가용 공간은 약 53.75GB였다. 별도 APFS 볼륨 조회에서 주 컨테이너의 Data 외 System·Preboot·Recovery·Update·VM 합계는 약 33.51GB여서 이들에 수백 GB가 몰린 것은 아니었다. 볼륨 사용량은 시스템 데이터라는 화면 분류와 다르며 시점에 따라 달라진다.

## Chrome의 큰 표시 크기는 별도로 해석

`/private/var/folders/j8/601m2kw5043683gyygwr2n580000gn/X/com.google.Chrome.code_sign_clone`에는 **638개** 디렉터리가 있다. `du`(폴더별 사용 블록 집계 도구)의 해당 경로 표시는 **962,652,987,392바이트, 약 962.65GB**다. 이 값은 당시 Data 볼륨 전체 사용량보다 커서 위 표에 합산하거나 독립적으로 점유·회수 가능한 물리 용량으로 읽을 수 없다. 같은 X 폴더의 AsideBrowser 표시는 약 1.695GB이며 Chrome 값에 포함되지 않지만 이 역시 독점 물리 용량으로 확정하지 않았다.

세 표본은 Chrome 앱 구조와 같은 버전을 보였고, 주 실행 파일은 설치 앱과 같은 inode(동일한 실제 파일을 가리키는 번호)·연결 수 639였다. 다른 실행 파일의 번호가 다르다는 사실만으로 APFS 내부 블록이 독립적이라고 단정할 수 없다. [Chromium 공식 소스](https://chromium.googlesource.com/chromium/src/+/lkgr/chrome/browser/mac/code_sign_clone_manager.mm)는 앱을 `clonefile`(저장 영역을 공유해 복제하는 기능)로 복제하고 주 실행 파일을 hard link(같은 파일에 이름을 더 붙임)로 연결하는 동작을 보여 준다. [Apple APFS 문서](https://developer.apple.com/documentation/foundation/about-apple-file-system)는 복제본이 바뀌지 않은 데이터 블록을 공유한다고 설명한다. 이 원리와 관측 구조는 일치하지만, 설치 버전과 최신 공개 소스의 완전한 일치나 638개 전체의 독점 물리 용량을 직접 증명한 것은 아니다.

따라서 **복제본 누적은 확인했지만 772.07GB의 범인 또는 삭제 회수량은 확정하지 않았다.** 실행 경로 조회에 복제본이 보이지 않았다는 결과도 모든 파일이 사용되지 않는다는 증거는 아니다.

## 측정 범위와 한계

- 홈의 주요 폴더·Project 직접 항목·CDS 작업 폴더·Applications·Data의 나머지 직접 항목·`/private/var`의 지정 범위와 APFS 볼륨을 나누어 읽었다. 상위 경로의 실패 뒤 별도로 완료된 직접 자식만 집계했다.
- `.DocumentRevisions-V100`·`.Spotlight-V100`·`.fseventsd`·보호된 시스템 자산과 `/private/var/root` 등은 권한이 막혔다. `folders/zz`는 한 번만 읽어 보이는 부분 483,328바이트와 권한 오류 77줄을 남겼다. 접근 거부는 크기 0이 아니라 미확인이다.
- j8 계정 전체 순회는 제한 시간에 끝나 전체 크기를 얻지 못했다. X 폴더 측정은 완료됐지만 서로 다른 시점의 경로 합계·공유 블록·스냅샷을 중복 합산하지 않는다. 활성 작업 때문에 파일도 변할 수 있다.
- 이번 **원인 진단에서 삭제·이동·앱 종료·권한 변경·관리자 권한 명령 실행은 0회**다. 별도로 승인받아 앞서 마친 Wavvy 정리는 1,298파일·52,534,148,348바이트의 실행 삭제이며, 이번 진단의 삭제로 합치지 않는다. 이전에 이미 없던 썸네일 PNG 두 개 역시 그 1,298개에 넣지 않는다. 이 기록은 이번 마감 기록에 포함한다.

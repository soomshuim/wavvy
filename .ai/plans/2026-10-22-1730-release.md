[정밀 비교](../../SERIES/17-30/input/validation/2026-10-22-internal-audio-test/compare-test2-fullrate-and-ab.json)는 같은 곡 구간의 좌·우 상관계수 약 0.996, mono 약 0.9973을 보였고 녹음 음량이 보정 없이 약 1.69 dB 크다. 원본과 바이트 동일한 파일은 아니다. 이 샘플은 이후 젠이 “통과.”라고 판단했다. 그 뒤 4번 전곡도 젠이 “통과 계속해.”라고 판단했고, 5~8번 내부 녹음을 추가 등록했다.

CoreAudio의 Aside 본체·오디오 helper 출력 관찰은 두 번 false였지만 정확한 원인은 미확인이다. 원시 WAV·도우미는 로컬 `work/2026-10-22-internal-audio-test/`에 보존한다. 젠은 브라우저 질문에 “3”으로 답해 Aside를 선택했다. 이후 기존 Suno 탭의 [추가 진단](../../SERIES/17-30/input/validation/2026-10-22-internal-audio-test/pilot2-coreaudio-during.json)에서 audio helper PID 73077의 `running_output=true`를 관측했다. 두 번째 로컬 시험 파일은 공식 원본의 같은 33.76초 구간과 시간 정렬·채널 상관을 대조했고 젠이 해당 샘플을 “통과.”로 판단했다. 그 뒤 4번 전곡의 젠 청취는 통과했고, 5~8번 내부 녹음을 추가 등록해 로컬 선택 WAV는 8/20이다.

## 내부 오디오 녹음 출처의 기록 (4번 한 곡 등록)

1번 곡의 두 번째 30초 시험은 원본 다운로드와 33.76초의 동일 구간을 비교했을 때 좌·우 상관계수 약 0.996, mono 약 0.9973, clipping 0, 측정 시간 drift 0이었다([전체 시험 요약](../../work/2026-10-22-internal-audio-test/pilot2-summary.json), [채널별 비교](../../work/2026-10-22-internal-audio-test/compare-test2-fullrate-and-ab.json), [시간 창 대조](../../work/2026-10-22-internal-audio-test/compare-test2-drift-windows.json)). 이는 **시험 구간**의 수신·시간 정렬 근거이며 남은 17곡의 완성이나 음질 판정이 아니다. 당시 별도 담당자는 4번 한 곡만 녹음해 젠의 전곡 청취 판정을 기다렸다. 이후 젠이 통과를 알렸고 5~8번을 등록해 로컬 선택 WAV는 8/20이다.

선례: [17:00 다운로드 manifest](../../SERIES/17-00/input/download-manifest.json)는 파일별 `download_actor`에 Suno 다운로드와 사용자 제공을 구분했지만 `source_kind`나 녹음 원본 연결은 없다. [07:00 manifest](../../SERIES/07-00/input/download-manifest.json)도 WAV별 후보 ID·해시·길이를 기록한다. [오디오 ingest 스킬](../../skills/wavvy-audio-ingest/SKILL.md)은 `download-manifest.json`의 순서·제목·선택 ID·파일 해시·형식 대조를 요구한다. 기존 경로와 필드를 유지하면서 이번 17:30의 각 트랙에 **추가 필드**로 실제 획득 방법을 표시한다.

- 이미 확보한 재생 1~3번은 각각 `source_kind: suno_official_download`로 적고 현재 `download_actor`, 파일별 48 kHz·스테레오·PCM 16-bit·SHA-256을 유지한다. 재생 4~20번은 완성·원시 근거 검증을 거친 곡만 `source_kind: system_audio_capture`로 추가한다. 녹음 항목의 `download_actor`는 다운로드가 아님을 명시하고 `capture_actor`에 실제 작업자를 적는다. 현재 4번 한 항목만 추가했고, 남은 16개 항목은 실제 파일·근거를 받을 때까지 만들지 않는다.
- 녹음 항목은 선택 `candidate_id`·`candidate_url`과 같은 ID의 실제 UI 재생 원시 근거, 앱 전용 캡처 방식·범위, `raw_capture_path`·SHA-256, 경계 처리·잘라낸 구간의 근거, 최종 `input_filename`·SHA-256·길이·probe(코덱·샘플률·채널·샘플 형식)를 분리해 적는다. 원시 녹음은 로컬 `work/`에 두고, 완성 검증본만 `input/tracks/`로 복사한다. 녹음 중 단편이나 무음 시험 파일은 manifest의 선택 음원으로 넣지 않는다. 곡마다 원시/최종 해시와 선택 ID가 맞는지 확인한 뒤에만 확보 수와 공식 state를 writer로 갱신한다.
- 기존 manifest 최상단의 `audio_format: 48 kHz stereo PCM 16-bit WAV`는 1~3번에 한해 참이었다. 4번 완성본을 probe해 현재는 혼합 형식으로 명시했고 **파일별** `codec`·`sample_rate_hz`·`channels`·`bits_per_sample`/`sample_format`을 기준으로 삼는다. float32라고 가정해 16-bit로 잘못 표기하거나 무검증 변환하지 않는다.
- 코드 읽기 결과 `resolve_playback_source_bindings`와 `verify_release_package`는 manifest의 순서·제목·선택 ID·WAV 해시·길이를 비교하지만 `source_kind`·캡처 UI 근거·원시 해시·경계 처리는 아직 검사하지 않는다. `validate_project`는 실제 음원의 코덱·길이·샘플률을 probe하므로 혼합 PCM 자체를 거부하지 않는다. 따라서 추가 필드 기록은 기존 릴리스 계약을 깨지 않지만 **기존 PASS만으로 녹음 출처가 검증됐다고 할 수 없다.** 4번 원시→최종·선택 ID·UI 재생·경계 처리는 [좁은 검사](../../SERIES/17-30/input/validation/2026-10-22-selected-audio-capture/04-ingest-verification.json)로 별도 대조했다. 이 출처 검사를 최종 출고의 자동 게이트로 만들려면 `verify_release_package`의 playback-order 분기에만 `source_kind=system_audio_capture` 검증을 추가하는 최소 코드 변경이 필요하며, 실제 첫 자료의 필드 형식을 확인한 후 범위를 확정한다. 이번 한 곡 등록에는 하네스 코드를 변경하지 않았다.

## 실행 순서와 게이트

1. 선택 ID 20개와 다운로드 WAV의 파일별 연결을 확보한다. [audio-ingest 스킬](../../skills/wavvy-audio-ingest/SKILL.md)의 해시·길이·코덱 검사 후 `input/tracks/`에는 재생 번호·현재 제목의 WAV를 둔다. Suno 다운로드 한도 때문에 아직 전곡이 로컬에 없으므로 전체 렌더와 최종 보고서는 대기한다.
2. 1번 WAV만으로 기존 `preview SERIES/17-30 --sec 30` 명령을 실행해 **1곡만 쓰는 임시 미리보기**를 만들었다. 30.000초, 3840×2160 H.264 영상과 48kHz 스테레오 AAC 오디오, 영상 프레임·오디오 디코드·thumb/loop/WAV 해시를 확인했다. 이는 20곡 영상이나 전곡 청취 통과가 아니다. 전체 20곡 확보 뒤 전곡 검증을 진행한다.
3. 제목은 현재 `Playlist | 기분좋아져라 🍊 | MODERN R&B · NEO SOUL | 기분전환 · 드라이브 | Wavvy | 17:30` 초안을 젠에게 확인 요청한 상태다. 현재 설명·태그도 초안이다. 승인된 제목만 최종 `concept.md`·`output/upload.csv`·YouTube에 사용한다.
4. 20 WAV 확보와 아래 출처 연결 차단점 해결 후 `validate`, 전곡 30초 preview, `pack -y`의 2회 반복, `report.json` 대조, 가사 원문 최종 보존, `prepare-subtitles`, `source-final`·`render-final`·`verify-release`를 진행한다. 실제 챕터 시작 시각은 `output/report.json`에서만 작성한다. 사람용 제목 번호는 `1.`처럼 앞 0 없이 쓴다.
5. 업로드 사본의 4K 영상·오디오·썸네일·설명·제목을 검증한 뒤, 젠이 **제목 전체를 승인한 경우에만** YouTube 업로드를 진행한다. 공개·예약 여부와 업로드 성공 여부는 실제 결과로 따로 기록한다.

## 읽기 전용 도구 대조에서 발견한 출처 연결 차단점

선례: [17:00 완성 시리즈](../../SERIES/17-00/concept.md)는 재생번호와 소스 제목이 같은 20곡을 `Final Track Sources`에 보관했고, [15:00 메타데이터](../../SERIES/15-00/concept.md)는 보고서 기반 Track List를 썼다. 이번에는 사용자 확정 재배열·개명과 Cover의 미확인 생성 입력 때문에 그 제목 매칭 선례를 그대로 적용하면 틀린 원문이 최종 음원의 실제 프롬프트인 것처럼 남는다. 따라서 이 도구 수정은 새 기능 추측이 아니라 승인된 릴리스의 출처 오염을 막기 위한 필수 작업이다.

- `wavvy.py:1708`의 `match_sources_to_report_tracks`는 `Track` 헤더/파일명과 렌더 보고서 제목만 비교한다. [순서 JSON](../../SERIES/17-30/input/playback-order.json)의 `source_order`를 읽지 않는다. 실제 현재 txt 20개와 재생 제목 20개를 함수에 넣으면 **17/20만 연결**되고 `오늘의 기록`(원20), `이 노래 끝날 때까지`(원13), `우리 행복하자`(원19)에 대해 `Missing txt source for report track(s)`가 발생한다. `wavvy.py:2165`의 `finalize_upload_sources`는 이 함수를 거치므로 그대로는 `--check`도 실패한다. `wavvy.py:2486`의 `prepare-subtitles`는 최종 원문 아카이브에 의존한다.
- `wavvy.py:1744`의 `verify_final_selection_source_provenance`는 선택 ID별 정확한 생성 원문 해시가 기록돼 있어야 통과한다. 그러나 12개 기존 Cover는 옛 txt가 현 생성 입력이 아니며 원13·19의 현 사용자 버전 생성 STYLE/EXCLUDE도 미확인이다. 제목을 맞추기 위해 옛 원문 파일 이름·헤더를 바꾸거나 `source_sha256`를 임의로 채우면 잘못된 생성 출처를 확정하게 된다. 원문과 이력은 보존하고, 실제 검증 가능한 가사와 생성 입력 미확인을 분리해야 한다.
- `wavvy.py:2003`의 `verify_release_package`에서 fallback 후보 검사는 report `order`를 후보 JSON의 `order`와 그대로 비교하고, `decision.status == "keep"` 및 생성 원문 `input/tracks` 해시를 요구한다. 현재 후보 JSON은 **원번호**를 키로 하며 결정은 `user_selected_for_20_song_sequence`다. 재생번호·원번호가 다른 19곡과 미확인 Cover 생성 원문은 기존 조건으로 정확히 표현할 수 없다. `suno-final-selection*.json` 분기를 사용하더라도 위 `finalize-upload` 생성 출처 검사는 별개로 남는다.
- `wavvy.py:2130` 부근의 `verify_release_package` 챕터 정규식은 `01.`처럼 정확히 두 자리 번호를 요구한다. 젠은 Suno 곡명과 사람용 번호를 `1.`로 확정했다. 잘못된 0 접두를 넣어 검사를 통과시키지 않는다.

차단점 해결은 `playback-order.json`의 검증된 slot으로 재생번호→원번호→선택 ID를 직접 잇고, 원문 아카이브에서 `가사 확인본`과 `정확한 생성 STYLE/EXCLUDE 확인본`을 분리한다. 다운로드 manifest의 선택 ID와 slot ID·재생번호·제목·WAV 해시를 함께 검증한다. 출처가 불명인 13·19 및 Cover 리믹스의 과거 txt는 생성 프롬프트로 표시하지 않는다. 사람용 챕터 파서는 한 자리와 두 자리 정수 번호를 허용하되 `report.json`의 순서·시각·제목과 일치해야 한다. [출처 연결 독립 검토](../reviews/2026-10-22-release-prep-review.md)는 CLEAN이었다. 그때 발견된 복수 대괄호 지시문 자막 누출도 수정했고 [분리된 diff](../../SERIES/17-30/input/validation/2026-10-22-release-source-binding/subtitle-fix-review-diff.txt)·[68회 검사](../../SERIES/17-30/input/validation/2026-10-22-release-source-binding/command-results.json)·[20곡 가창행 대조](../../SERIES/17-30/input/validation/2026-10-22-release-source-binding/subtitle-direction-check.json)를 남겼다. [자막 수정 독립 검토](../reviews/2026-10-22-subtitle-fix-review.md)도 CLEAN이다. 20곡 보고서는 WAV 17개 부족으로 아직 만들 수 없으므로 실제 `finalize-upload --check`와 `verify-release` 전수 실행은 대기다.

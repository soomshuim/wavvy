# 06:30 거부6곡의 선택 원본 영구 삭제 후 정상 업로드 재시도

## 최초 일반 휴지통 한정 계획 — 아래 영구삭제 지시 전 이력

- 새 사용자 원문: “6,9,11,12,17,19는 suno에서 먼저 삭제하고 업로드 시도”. 직전의 로컬 삭제로도 읽힐 수 있던 표현은 이 Suno 한정 정정이 우선한다.
- 선례: `input/suno-replacement/2026-10-24/replacement-manifest.json`의 기존33 일반 휴지통 이동·신규14·거부6 상태와 `input/download-manifest.json`의 최종20파일이다.
- 범위: 같은 Suno 작업공간335455f4-30d5-4878-b658-365da757127e에서 여섯 번호의 기존 버전이 활성 목록에 남아 있는지 확인한다. 기존 버전이 있으면 안정된 ID로 확인한 해당 기존 곡만 일반 휴지통 이동한다. 이전 완료된 삭제를 새 삭제로 중복 집계하지 않는다. 기존33은 이미 휴지통으로 이동한 상태이며 영구삭제 지시는 없으므로 영구삭제로 확대하지 않는다.
- 이어 동일한 승인 최종파일6개를 정상 업로드 화면에서 각1회 재시도한다. 이전14개 업로드·다른워크스페이스·로컬/Downloads/선택원장/원본은 보존한다. 음악 변경·자르기·생성·공개·서비스 검사 우회는 하지 않는다.
- 브라우저: Aside/MCP `mcp__aside__repl`, 동일 Profile0. 실행은 기존 Sol6.1/xhigh 워커가 맡고 컨트롤러는 원시증거/실제파일을 대조한다. 컨트롤러는 현재 환경 override Sol6.1/xhigh 그대로이며 전환을 주장하지 않는다.
- 결과는 별도 재시도 원장과 원시 화면에 저장한다. 성공이 생기면 새 ID·제목·길이·현재 집합을 확인하고 이전 원장을 역사로 보존한다. 같은 오류면 원인을 단정하지 않고 거부 상태를 유지한다. 정상 재시도는 각1회이며 반복하지 않는다.
- 이후 실제 결과에 맞게 concept/SESSION/HANDOFF/CHANGELOG를 기록하고, 독립 Astra/high 검토와 범위 내 확인 후 커밋·푸시한다. Suno 작업은 YouTube uploaded 상태가 아니다.

## 사용자 추가 지시로 범위 확정

- 최신 원문: “영구 삭제 하고 재시도”. 따라서 앞의 일반 휴지통 한정은 이 추가 지시로 대체한다. 로컬 삭제를 뜻하지 않는다.
- 삭제 대상은 최종 선택 원본6개 ID로 동결했다. 같은 번호의 모든 생성 후보·다른 시리즈·휴지통 전체로 확대하지 않는다. `work/0630-suno-retry-six-20261024/frozen-six-targets.json`의 source_candidate_id6개만 정상 Suno 휴지통 UI에서 영구삭제한다. 12번 선택 원본은 이전33개 목록에 없지만 과거 이미 휴지통에 있던 원본이므로 정확한ID로 찾는다.
- 컨트롤러가 6개 최종 로컬 WAV의 실제 SHA를 최종 원장과 대조했으며 모두 보존돼 있다. 원본 생성 ID는 출처 이력으로 보존하고 영구삭제 사실은 새 별도 원장에 연결한다. 새 업로드 ID로 과거 출처 ID를 덮어쓰지 않는다.
- 영구삭제 안내가 나오면 사용자 위 지시가 해당6개에 대한 실행 승인이다. 추가 확인을 반복해서 묻지 않는다. UI에서 대상 ID를 검증할 수 없거나 해당 ID를 못 찾으면 임의 후보를 대신 삭제하지 않고 보고한다.
- 정확한6개 영구삭제 후 동일 최종파일6개를 정상경로로 각1회 재시도한다. 원인 추정·음원변형·검사우회·연쇄재시도는 하지 않는다.

## 최신 실행 범위 — 사용자가 직접 삭제

- 사용자 최신 원문 “내가 삭제했어.”가 반복 수신됐다. 따라서 에이전트의 영구삭제 준비를 즉시 중단하고 같은 워커를 interrupt한 뒤 업로드만 재배정했다. 에이전트가 추가 삭제·복원을 실행하지 않는다. 위 영구삭제 배정은 사용자 직접 삭제 이전 준비 이력이다.
- 직접 삭제 완료는 사용자 보고로 분리한다. 에이전트의 실제 영구삭제 UI 근거 없이 agent-executed 또는 independently verified라고 기록하지 않는다. 이미 관찰한 옛 Trash 화면을 현재 상태로 잘못 인용하지 않는다.
- 남은 실행은 동일 최종파일6개의 정상 업로드 각1회 재시도와 실제 결과의 별도 원장 기록이다. 삭제 확인만을 위해 Trash를 계속 순회하지 않는다.

## 사용자 후속 재시도 지시 — 파일 이름 변경 후 필요하면 1 BPM 감속

- 추가 원문 “강제 새로 고침 후 다시 업로드해봐. 이름도 좀 바꿔보고”. 이어 “재시도해도 안되면 음원도 길이를 수정해. 1bpm 정도 느리게”. 같은 여섯 곡에만 적용한다.
- 삭제 보고 뒤 첫 재시도는 여섯 파일 각1회, 성공0·거부6·대기0이었다. 별도 `retry-six/retry-manifest.json`과 원시 대기열을 역사로 보존한다. 이 결과를 덮어쓰지 않는다.
- Aside/MCP 공식 guide에 cache 우회 reload 옵션은 없다. 공식 keyboard.press로 mac 강제 새로고침 단축키를 한 번 보내고 실제 화면을 관찰한다. 단축키 입력과 캐시 우회 검증을 분리한다. 실행 오류나 재로딩 관찰 부재면 문서화된 page.reload 한 번으로 화면을 새로 읽고 그 한계를 명시한다. 다른 브라우저·연결 방식으로 전환하지 않는다.
- 같은 바이트의 전송 사본6개를 영문 이름으로 바꾸고 각1회 정상 업로드한다. 별도 `retry-renamed/` 원장에 기록한다. 영구 곡명 변경 지시로 확장하지 않으며 성공하면 기존 번호·한국어 곡명을 유지한다.
- 이 이름변경 배치에서도 거부된 곡만 1 BPM 정도 느린 별도 WAV를 만든다. 대상6곡은 기존176처리목표이므로 FFmpeg atempo=175/176, 음높이 유지, 전체 길이 기대배수176/175를 쓴다. 앞뒤 자르기·무음 추가·음높이/음색/볼륨 변경은 하지 않는다. 175는 처리 목표이며 실제 모든 순간의 정확한 BPM을 인증하지 않는다.
- 감속 사본은 기존 승인 입력과 분리된 `input/suno-replacement/2026-10-24/retry-slower/`의 별도 목록과 ignored work 폴더에 둔다. 원본 local20·Downloads20·기존 download-manifest/candidates/state는 덮어쓰지 않는다. 새 원격 업로드는 원본 출처 ID·기존 최종 SHA·감속 사본 SHA·새 업로드 ID를 모두 구분해 연결한다.
- 가장 먼저 실패 곡 하나를 전체 처리해 기대 길이·형식·유한 표본·클리핑·내부 끊김을 검사한 뒤 나머지 실패 곡을 처리한다. 전체 결과가 기술 검사를 통과하면 정상 업로드 각1회 실행한다. 기술 검사가 실패하면 자동 수정 반복을 하지 않고 보고한다.
- 이 후속 지시로 이름변경·감속 재시도가 허용됐지만 새로고침/이름/감속으로 서비스 거부 원인이 해결된다고 단정하지 않는다. 새 원장을 합쳐 현재 실제 원격 집합과 미완료 곡을 기록하고 독립 검토 뒤 마감한다.
